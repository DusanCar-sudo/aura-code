Patch bay model

The visual system follows the repo architecture.

The orchestrator creates two to four contracts, routes independent groups in parallel, and stores the resulting traces. The design uses wires, sockets, and ledger rows because the repo is about constrained handoffs, not generic agent sparkle.

Full workflow preview

See the whole run, not just the handoff.

This preview covers the full AgentMesh loop exposed in the repo: decomposition, bounded execution, hard gates, aggregation, memory, and future routing.

01Goal intake

The CLI accepts a natural language goal plus optional provider, model, workspace, and streaming flags.

02Plan

The orchestrator breaks the goal into two to four contracts and groups independent tasks for parallel work.

03Dispatch

Research, code, writer, file, data, or summary agents receive only their permitted tools and budget.

04Gate

Condition checks inspect real outputs: required keys, output files, summaries, and error flags.

05Aggregate

Successful task results are collected into the final JSON output and written back into the workspace.

06Learn

Episodes, lessons, and skill stats are stored so later runs can adapt provider and tool choices.

Run surface

Source install, direct goal, visible status.

The commands mirror `run.py` and `pyproject.toml`: local install, provider choice, streaming output, and memory status.

$ git clone https://github.com/DusanCar-sudo/agentmesh.git
$ cd agentmesh
$ python -m pip install -e .
$ python run.py --provider deepseek --stream "Build a CLI report"
[Orchestrator] 3 contracts across 2 groups
[agent_code] output_file_exists
[Memory] episode stored in workspace/memory.db
